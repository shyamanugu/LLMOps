01 The big picture

One reusable platform, many use cases

The work is not a single call-analytics application. It is a standardized LLMOps platform — a common foundation for deploying and operating any number of LLM-based use cases. Apex, AFNI's contact-center performance pipeline, is simply the first use case that runs on it and proves it works.

In plain terms: we built the factory, not just one product. Apex is the first thing off the line. Each new use case reuses the whole factory and only supplies its own recipe — its data, its prompts, and how it wants to be measured.

The platform

Reused by everyone
  • Provides the operational muscle every LLM use case needs: prompt & model management, evaluation, observability, guardrails, feedback and controls.
  • Onboard by configuration — a new use case adds only its own config and evaluation data; no re-plumbing.
  • Improve without code changes — an evaluation gate before deployment, and prompt-level tuning after it.

A use case (Apex)

Its own recipe
  • Scores 100% of weekly calls into per-agent coaching, across three Verizon lines of business.
  • Supplies only what's unique to it: the evaluation schema, the prompts, the KPI definitions and its golden data.
  • Plugs into the platform at a single, fail-open connection point — a platform hiccup never breaks a run.

Future use cases already in view — hiring intelligence, agent knowledge-assist, automated quality-scoring, coaching-plan generation — inherit the same platform and add only their own configuration. That reuse is the strategic value; Apex demonstrates it end to end.

02 The platform, capability by capability

What every use case gets for free

Seven capabilities make up the platform. All seven are already integrated into Apex through a single connection point, so the pipeline benefits from them today without carrying their complexity in its own code.

1

Prompt Management

Prompts live in a versioned registry, separate from application code. A prompt engineer edits and tests a prompt, and — once approved — promotes it as a new version. The running system picks it up without a code release.

Why it matters: most quality improvements are prompt changes; this makes them safe, tracked and independent of engineering.
2

Model Management

Code refers to a model by a stable alias (e.g. reason, bulk), not a hard-coded deployment name. A registry maps aliases to actual models per environment, and resolution is fail-open.

Why it matters: swap or upgrade models by config, per environment, with zero code change and no risk of a bad lookup breaking a run.
3

Evaluation Gate

Before a prompt/model change ships, it is scored against a curated "golden" dataset. The gate reports quality plus token usage, cost and latency. Below the required threshold, the change is rejected rather than deployed.

Why it matters: quality is measured before customers see it — no more "ship and hope."
4

Observability

Every model call is traced with its step context, token counts, latency and cost, so runs can be monitored, debugged and costed after the fact.

Why it matters: operational visibility into a system that makes thousands of model calls per run.
5

Guardrails & Audit

Checks such as PII detection run on the way through, and flagged events are recorded for review rather than silently dropped. Each use case applies the policy appropriate to it.

Why it matters: compliance and safety with an auditable trail, not a black box.
6

Feedback Loop

Application users — for Apex, coaches — rate a generated result (1–5) and add comments. Feedback is stored so a maintenance engineer can revise prompts and, where justified, expand the evaluation dataset.

Why it matters: production experience flows back into measurable improvement.
7

Operational Controls

Rate-limiting, retries, timeouts and a mock/real switch keep large runs within provider limits and let the pipeline be exercised safely without live calls.

Why it matters: reliability and cost-control at the scale of scoring every call, every week.
03 How Apex works

From raw call to per-agent coaching, in five steps

Apex runs weekly. It takes raw contact-center call transcripts and turns them into a coaching scorecard for every agent. Each step feeds the next; the model is used where judgment is needed and plain computation is used everywhere else.

In plain terms: the pipeline reads every call, judges what happened on it, adds up those judgments per agent over the week, blends in operational numbers from Verizon's systems, and writes one weekly file the coaching dashboard reads.
STEP 1

Denoise

Cleans raw, messy speech-to-text transcripts into readable form so later steps judge content, not transcription errors.

raw → clean transcript
STEP 2

Analysis

Scores every single call against the program's evaluation schema — behaviours, outcomes, sentiment — each with the call segments that justify it.

call → structured evaluation
STEP 3

Summary

Rolls a full week of a coach's calls into per-agent KPIs and behaviour scores, and writes a coaching narrative.

week of calls → scorecard
STEP 4

Individual metrics

Adds each agent's operational metrics from Verizon's data warehouse and generates tailored coaching tips from the trends.

+ AHT / VXS / resolve
STEP 5

KPI aggregator

Flattens everything into the single weekly file the dashboard consumes, with roll-up scores per agent.

→ dashboard CSV

A defining strength: every judgment the model makes is backed by evidence — the specific call segments that support it are recorded alongside the result. Coaching is auditable, not a black-box score.

Three programs, three lenses

The same pipeline serves three Verizon lines of business. Each has its own evaluation schema, prompts and KPIs, because "a good call" means something different in each.

Telesales

WCC

Wireless Customer Care — a care & retention lens across LEARN / PROVIDE / CLOSE phases: resolution, saves, right-of-sell. 11 KPIs.

PSO

04 The metric system

How one call becomes a set of measurable KPIs

This is the heart of Apex. Understanding it is what lets us evaluate and improve the system with confidence. There are four kinds of metric, produced in a clear chain.

The chain: the model judges each call (true/false, a rating, a score) → those per-call judgments are added up per agent into KPIs and behaviour scores → operational numbers from Verizon's warehouse are joined in → a few roll-up scores summarize the week. A prompt only ever changes the first link; everything after it is arithmetic.

1 · KPIs

Counts and rates of behaviours and outcomes — e.g. how many new-line pitches, what share of calls resolved. Derived by adding up the per-call flags.

2 · Behaviour & soft-skill scores

How consistently an agent shows a skill (active listening, empathy, clarity…), expressed as a 0–1 average across their calls.

3 · Operational metrics

Handling time, VXS, resolution and disconnect rates — pulled from Verizon's data warehouse. Not produced by the model.

4 · Roll-up scores

A composite performance score, risk counts and a status label that summarize an agent's week for the manager view.

A note on the operational metrics

Handling time (AHT), VXS, resolution and disconnect rates come from Verizon's data warehouse, not from the model. They are joined into each agent's scorecard as this-week-vs-last-week trends and feed the coaching tips — but because the model never computes them, they are validated as data queries, not as model output. This distinction matters for evaluation (next section).

05 Evaluation & golden data

How we prove the system is right — and keep it right

To improve prompts safely we need "ground truth": examples where the correct answer is agreed. The challenge raised in review was real — Apex KPIs are aggregated across many calls, so a naïve "one transcript → one KPI value" cannot validate them. The resolution is to recognize that a prompt change can only affect one part of the system, and to evaluate each part the right way.

L1
Call-level analysis
The per-call true/false, ratings and scores the model produces
Golden set — SME-certified labels
L2
Aggregation into KPIs
Counts and rates — plain arithmetic over the call-level results
Unit tests · no golden data
L3
Coaching narrative
The weekly reflection & recommendations per agent
SME rubric / judge
SQL
Operational metrics
AHT, VXS, resolution rate — from Verizon's warehouse
Validate the query
Certify the call-level judgments and unit-test the arithmetic, and every aggregate KPI is correct by construction. The metrics business worried about most — AHT, VXS, resolution rate — aren't model outputs at all, so golden data doesn't apply to them.

What makes a transcript "golden"

Not random selection — deliberate coverage of the decision space, plus reviewer agreement:

  • Coverage: the set must include calls that exercise each decision — with and without each opportunity type, each customer-experience rating, escalations vs none, each program, and edge cases (dropped calls, transfers, ambiguous intent).
  • Balance: enough positive and negative examples of each field to measure both precision and recall; rare-but-critical fields (escalations, saves) are deliberately over-sampled.
  • Agreement: each call labelled by two or more coaches; kept only where they agree. Where they disagree, the definition is unclear — a signal to fix before the record can be golden.

The workflow

A

Sample

Pick transcripts against the coverage matrix, per program.

B

Pre-label

Run the current model to give reviewers a starting point.

C

SME review

Coaches correct the field values and confirm the evidence.

D

Adjudicate

Keep records where reviewers agree; freeze as a version.

E

Gate & grow

Score prompts against it; feedback adds new scenarios.

Once a golden set exists, the evaluation gate does the rest: a prompt engineer selects the dataset, a model and a prompt, and runs it. The gate reports quality alongside token usage, cost and latency; below the required threshold the change is rejected. Approved prompts are saved as a new registry version — all without a code change.

08 Glossary

Terms used in this document

LLMOps platform
The reusable foundation for building, evaluating and operating LLM use cases — the "factory."
Apex
AFNI's contact-center performance pipeline; the first use case running on the platform.
Use case
One application built on the platform, supplying its own schema, prompts, KPIs and data.
KPI
A key performance indicator — a count or rate derived from the per-call evaluations.
Schema
The fixed structure of fields the model fills in for each call (booleans, ratings, scores).
Denoise
Cleaning raw speech-to-text transcripts before analysis.
Reflection
The model-written weekly coaching narrative for an agent.
Segment IDs
References to the specific call parts that justify a judgment — the evidence trail.
Golden dataset
Curated examples with business-certified correct answers, used to evaluate changes.
Ground truth
The agreed-correct answer for an example, certified by coaches or SMEs.
Evaluation gate
The check that scores a prompt/model against the golden set before deployment.
Guardrails
Safety/compliance checks (e.g. PII) recorded for audit rather than silently dropped.
AHT / VXS / FCR
Operational metrics: average handling time, Verizon experience score, first-contact resolution.
SME
Subject-matter expert — here, coaches and the internal Apex specialists.
