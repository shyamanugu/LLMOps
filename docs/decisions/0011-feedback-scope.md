# ADR 0011: Feedback Loop — no Orchestration change, promotion as a data bridge

## Status
Accepted

## Context
Every gating mechanism this platform has built so far (Evaluation Gate, Guardrails) works against curated or synthetic cases. Real production mistakes, once a human corrects them, should become permanent regression tests — otherwise the same mistake can silently reoccur after the person who caught it has moved on. This component is where that correction gets captured and turned into something Evaluation Gate can actually run.

Two design questions: does this integrate into Orchestration the way Observability just did, and how does a corrected output become a golden-dataset case without creating a hard dependency on Evaluation Gate's internal types.

## Decision
1. **No change to Orchestration (08).** Feedback is collected after a human has seen an output — an agent reviewing a suggested reply, a customer rating an interaction — not during a `Step`'s `.run()`. Unlike Observability (ADR 0010), there's no natural per-step hook to add, because this isn't a per-step concern; it's correlated to a run via `session_id` (already generated by `State`) as plain string matching, not an import.
2. **Three `FeedbackStore` implementations**: `InMemoryFeedbackStore` (tests), `JsonlFileFeedbackStore` (zero-Azure default), `AzureBlobFeedbackStore` (real backend, lazy SDK import, not exercised by the automated test suite — same posture as every other real-Azure backend in this platform).
3. **`promote_to_golden_dataset()` is a data-format bridge, not a code dependency on Evaluation Gate (04).** It writes JSONL lines matching that component's documented golden-dataset schema (`docs/decisions/0008-evaluation-gate-scope.md`) without importing `evaluation_gate`. A wrong guess about that format fails loudly the moment `evaluation_gate.dataset_loader.load_dataset()` tries to read the file — an acceptable failure mode for a format-compatibility bridge between two independently-versioned components.
4. **`FeedbackEvent` carries `original_input`, not just `corrected_output`.** A correction is only a useful regression case if the input that produced the wrong answer is captured too — without it, promotion would produce a golden-dataset case with no input to run against.
5. **Only corrected feedback is promoted.** A plain thumbs-up/down has no comparison value as a golden-dataset case (there's no "expected" to check against) — it's a quality signal that currently has nowhere else to go.

## Alternatives Considered
- **Adding a `feedback` hook to Orchestration's `Step`/`Pipeline`**, mirroring the `tracer` parameter: rejected — feedback isn't produced during a run, it's collected afterward by something outside the pipeline entirely (an agent's UI, a customer survey). Adding an unused hook to Orchestration for a concern that doesn't fire during execution would be built-ahead-of-need, the same mistake already avoided for Key Vault (ADR 0001) and voice infrastructure (ADR 0003).
- **Importing `evaluation_gate.types.EvalCase` directly** to build promoted cases: rejected — it would create a real code dependency between two components whose only actual coupling is a shared file format, and would make this component's tests require Evaluation Gate's package on the path for no functional benefit.
- **Promoting ungated thumbs-up/down feedback too** (e.g., as a low-confidence golden-dataset case): rejected — there's no "expected" value to check a future run against, so it wouldn't function as a regression test, only as noise in the dataset.

## Consequences
- This is the third fully standalone component (alongside Guardrails and Evaluation Gate's core evaluators) — no other platform component is a prerequisite, and nothing in this platform yet calls into it. It's built ahead of a caller, same as Evaluation Gate was built ahead of CI/CD.
- The promotion bridge's correctness depends on the two components' JSONL schemas staying compatible by convention, not by a shared type — a future schema change to Evaluation Gate's golden-dataset format needs a corresponding update here, caught by whoever tries to load a promoted file, not by an import-time type check.
- Plain ratings (thumbs-up/down with no correction) are captured and stored, but have no consumer yet — they're not lost, just not yet feeding anything downstream.

## Revisit When
- A real usecase's serving layer (component 10) exists and needs to actually call `FeedbackStore.record()` — that's the first real caller this component has been built ahead of.
- Plain (uncorrected) ratings need to feed something — e.g., aggregate satisfaction metrics into Observability (05), or flag low-rated-but-uncorrected sessions for human review. Neither is built now because no usecase has defined what that downstream consumer should look like.
- Evaluation Gate's golden-dataset schema changes — update `promote_to_golden_dataset()`'s output shape to match, and treat it as a signal this data-format bridge might be better served by a shared schema definition instead of independent documentation.
