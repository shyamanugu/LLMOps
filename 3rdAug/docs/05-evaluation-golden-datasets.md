# Evaluation & Golden Datasets

## Why this document exists

A large language model (LLM) does not fail like normal software. It does not throw a stack trace when it is wrong — it gives you a fluent, confident, wrong answer. You cannot catch that with a unit test that checks `output == expected`. You catch it by running the same set of test cases against the model every time something changes (a prompt edit, a model swap, a retrieval tweak) and scoring the output on multiple dimensions. That test set is the golden dataset, and the scoring layer is the evaluation framework. This document describes exactly how to build both, which tools to score with, and how to wire the result into a continuous integration (CI) gate so a bad change cannot merge.

## What a golden dataset actually is

A golden dataset is a curated, versioned list of test cases for one use case. Each case has:

- An **input** (the user query, plus any context the app would normally retrieve, e.g. retrieved chunks for a retrieval-augmented generation, or RAG, use case).
- An **expected output**, or — when there is no single correct wording — **grading criteria** (a rubric) that a judge can use.
- **Metadata**: intent/category, difficulty, source, and the date it was added.

It is not a test log and it is not raw production traffic dumped as-is. Every case in it has been looked at by a person (or was authored by one) and is trusted to represent something the system must get right. If a case turns out to be ambiguous or wrong, it gets fixed or removed — a golden dataset with bad cases in it will pass changes that should have failed and fail changes that were actually fine.

### Example record (JSONL)

Golden sets are stored as JSON Lines (JSONL) — one JSON object per line, so cases can be added, diffed, and reviewed in pull requests (PRs) like code.

```json
{
  "id": "billing-042",
  "use_case": "billing-support-assistant",
  "input": {
    "query": "Why was I charged twice this month?",
    "context": [
      {"doc_id": "kb-billing-017", "text": "Duplicate charges are usually caused by a retried payment after a declined card..."}
    ],
    "conversation_history": []
  },
  "expected_output": "Explain that duplicate charges are typically a retry after a declined payment, offer to check the account, and never promise a refund without checking the ledger.",
  "grading_criteria": {
    "must_mention": ["retry after declined payment", "will check the account"],
    "must_not": ["promise a refund", "blame the customer"]
  },
  "metadata": {
    "intent": "billing_dispute",
    "difficulty": "medium",
    "source": "sme_authored",
    "added_on": "2026-05-14",
    "added_by": "sme_review_batch_3"
  }
}
```

For cases with one correct short answer (extraction, classification), `expected_output` is a literal value instead of a rubric, e.g. `"expected_output": "duplicate_charge"`.

## How many examples to start with

Start with **50–200 examples per use case**. Fewer than 50 and the pass rate is too noisy to trust (one bad case swings the score a lot); more than 200 at the start slows down PR checks and SMEs (subject matter experts) run out of patience reviewing them. Split roughly:

- 60% common/happy-path cases (the bread-and-butter traffic).
- 25% edge cases (ambiguous input, missing context, multi-turn).
- 15% adversarial/safety cases (prompt injection attempts, policy-sensitive topics).

Grow the set over time as production traffic surfaces new failure modes — see the rotation section below.

## Where the examples come from

| Source | What it is | How to produce it |
|---|---|---|
| **SME-authored** | Subject matter experts write cases from domain knowledge, before the system has real traffic | Give SMEs a template spreadsheet/JSONL and a short rubric-writing guide; review in pairs |
| **Anonymized real traffic** | Cases mined from production traces (via the observability pipeline) and feedback signals | Pull traces with negative feedback, escalations, or low eval scores; strip personally identifiable information (PII); have an SME confirm the expected output |
| **Synthetic + human review** | Cases generated by an LLM (varying wording, edge conditions, adversarial phrasing) then reviewed by a human before they enter the set | Generate in batches, use a fast reviewer pass (accept/reject/edit), never let ungraded synthetic cases into the golden set |

A healthy golden set mixes all three. SME-authored covers what SMEs think matters; mined traffic covers what customers actually ask; synthetic fills gaps (rare edge cases SMEs did not think of, or that have not happened yet in production).

## Where it lives and how it is versioned

Golden sets are stored as JSONL files under `/evals/<use-case>/golden-v<N>.jsonl` in the same Git repository as the prompts and agent code. Changes go through a pull request like any code change:

```
/evals
  /billing-support-assistant
    golden-v3.jsonl
    evaluator-config.yaml
    CHANGELOG.md
  /claims-intake-agent
    golden-v1.jsonl
    evaluator-config.yaml
```

- `golden-v<N>.jsonl` — the dataset itself. Bumping the version number is required whenever cases are added, removed, or their expected output changes materially (not for typo fixes).
- `evaluator-config.yaml` — which evaluators run against this set and their thresholds (see the CI gate section).
- `CHANGELOG.md` — one line per version bump: what changed and why, and who approved it (SME sign-off for content changes).

Git is the source of truth, but the same dataset is **mirrored to Langfuse and/or Microsoft Foundry datasets** so non-engineers (SMEs, product managers) can browse cases, run ad-hoc evaluations from a UI, and add cases without opening a pull request. A small sync step in CI (`sync-datasets.yml`) pushes the JSONL to Langfuse's dataset API and to Foundry's evaluation dataset API whenever `/evals` changes on the main branch, so the UI copies never drift from Git.

## Metrics catalog

| Metric | What it measures | How it is scored | Typical gate |
|---|---|---|---|
| **Groundedness** | Whether the answer is supported by the retrieved context (anti-hallucination) | Azure AI evaluation SDK groundedness evaluator, or LLM-as-judge against the retrieved chunks | ≥ 0.90, blocking |
| **Relevance** | Whether the answer actually addresses the question asked | LLM-as-judge with rubric | ≥ baseline, no regression |
| **Retrieval precision** | Of the chunks retrieved, how many were actually relevant | Compare retrieved doc IDs to a labeled relevant set | ≥ 0.80 (tune per index) |
| **Retrieval recall** | Of the relevant chunks that exist, how many were retrieved | Same labeled set, recall@k | ≥ 0.85 at k=5 (tune per index) |
| **Coherence / fluency** | Whether the text reads as well-formed language | LLM-as-judge, low priority metric | advisory only |
| **Similarity to reference** | How close the output is to a known-good reference answer | Semantic similarity (embedding cosine) or Ragas answer-similarity | ≥ baseline |
| **Exact match / F1** | Correctness of a single extracted field or classification label | Reference-based string/label comparison | ≥ 0.95 for structured extraction |
| **Tool-call pass rate** | Whether the agent called the right tool with the right arguments | Deterministic assertion against tool-call logs | ≥ 0.95, blocking for agent use cases |
| **Task success rate** | Whether a multi-step agent achieved the end goal | Scenario suite: run the full flow, check final state | ≥ 0.90, blocking |
| **Steps / efficiency** | How many turns or tool calls it took to finish | Count against an expected step budget | advisory, flags runaway loops |
| **Handoff correctness** | Whether a router/supervisor agent sent the case to the right specialist agent or human | Deterministic assertion on the routing decision | ≥ 0.95, blocking |
| **Latency (p50/p95)** | Response time under load | Measured from traces during eval run | p95 under use-case SLO (service level objective) |
| **Cost per request** | Token cost of a single eval case | Token counts × model price, from traces | flag if cost per request grows > 20% versus baseline |
| **Safety** | Attack success rate (jailbreak/injection) and PII leak rate | Adversarial prompt suite + Content Safety scan | 0 tolerance on PII leak, blocking |

## Evaluator tools compared

| Tool | Best for | When to use it |
|---|---|---|
| **Azure AI evaluation SDK** | Built-in evaluators (groundedness, relevance, coherence, fluency, similarity) plus custom evaluators in Python, native to Microsoft Foundry | Default choice on the Azure stack; use when you want results to show up natively in Foundry's evaluation UI and link to traces |
| **Ragas** | RAG-specific metrics (faithfulness, context precision/recall, answer relevancy) with an open-source Python library | Use for RAG-heavy use cases where you want detailed retrieval diagnostics beyond what Azure AI evaluation SDK ships out of the box |
| **promptfoo** | Config-file-driven evaluation (YAML), runs from the command line, plugs directly into CI | Use for fast PR-time checks on prompt changes — it is the lightest-weight option to wire into `pr-checks.yml` |
| **LLM-as-judge with rubric** | Free-text quality grading against explicit criteria, using a strong model as the grader | Use when there is no single correct answer and a rubric captures "what good looks like" better than a reference string |
| **Human review** | Ground truth calibration, catching what automated graders miss, judging tone/empathy | Use for a sampled subset every release (5–10% of cases) to catch judge drift and to calibrate the LLM-as-judge's scoring against real human judgment |

In practice, most use cases run two or three of these together: Azure AI evaluation SDK or Ragas for the numeric metrics, promptfoo as the CI runner that calls them, and a human-reviewed sample as a periodic sanity check.

## The CI gate

Every pull request that touches a prompt, an agent definition, or a retrieval config triggers an evaluation run. The mechanics:

1. `pr-checks.yml` runs a **small subset** of the golden set (fast, cheap — usually 20–30 cases) scoped to whatever changed.
2. The candidate's scores are compared against the **last known-good baseline** stored from the previous successful run on the main branch.
3. If any blocking metric drops more than the configured threshold (for example, groundedness drops from 0.92 to 0.85, more than a 5-point drop), the PR check fails and the merge is blocked.
4. On merge to main, `eval-full.yml` runs the **entire golden set** (all 50–200+ cases) and posts a scorecard as a PR comment or job summary — this is the record kept for audit and trend tracking.

```yaml
# evaluator-config.yaml (excerpt)
use_case: billing-support-assistant
evaluators:
  - name: groundedness
    tool: azure_ai_eval_sdk
    threshold: 0.90
    blocking: true
  - name: relevance
    tool: azure_ai_eval_sdk
    threshold_regression: 0.05   # fail if score drops more than 5 points vs baseline
    blocking: true
  - name: retrieval_recall_at_5
    tool: ragas
    threshold: 0.85
    blocking: false
```

A candidate that regresses a blocking metric cannot promote past the PR check, full stop — there is no manual override baked into the pipeline; an override requires an explicit approval from a code owner on `/evals`, logged in the PR.

## Eval overfitting risk and rotation

The moment a golden set becomes the only thing engineers optimize against, it stops measuring quality and starts measuring "does this pass the golden set" — teams start tuning prompts to the specific wording of the 150 cases rather than to the underlying task. This is eval overfitting, and it is a known failure mode, not a hypothetical one.

Mitigations:

- **Rotate in new cases regularly** — every sprint or two, pull 5–10 new cases from recent production traffic (mined and reviewed per the sourcing table above) and retire an equal number of the oldest, most-passed cases to a "regression archive" set that still runs but is not the primary optimization target.
- **Hold out a portion of the set** — keep 20% of cases hidden from day-to-day prompt engineering and only run them at release time, so day-to-day tuning cannot directly fit to them.
- **Track score-vs-production gap** — if the golden set score is climbing but production feedback/complaint rate is flat or worse, that is the signal that overfitting has happened; treat a growing gap as a trigger to refresh the set.
- **Never let one person both write the golden set and grade the PR** — require SME sign-off separate from the engineer making the change, so the incentive to "make the eval pass" is checked by someone without that incentive.
